# 研究 Agent 系统设计方案（Agent Laboratory 风格）

## Context

目标：构建一个能够**自动写实验代码、跑实验、撰写论文**的多智能体系统，对标 Agent Laboratory（Schmidgall et al., 2025, *Using LLM Agents as Research Assistants*）。输入是一个人类提供的研究想法（research idea + 可选数据集/代码库），输出是实验代码、实验结果与一篇结构完整的论文（LaTeX）。

已与用户对齐的三个关键取向：
- **Harness 底层**：基于 **Claude Agent SDK**（复用其 subagent / 工具 / 会话能力做编排，自研角色层与流程层）。
- **自治程度**：**全自动 + 关键检查点**（co-pilot 模式，在选题、实验设计、投稿前等节点暂停等待人确认）。
- **执行环境**：**Docker 容器沙箱**（每次实验在隔离容器内运行，资源受限、可复现）。

本方案只描述架构设计，不含代码实现细节。重点在 multiagent harness。

---

## 一、整体架构（三层）

```
┌─────────────────────────────────────────────────────────────┐
│  Workflow Layer  阶段编排：文献综述 → 实验 → 论文撰写            │
│  （状态机 + 检查点）                                            │
├─────────────────────────────────────────────────────────────┤
│  Harness Layer  多智能体运行时（本方案重点）                    │
│  Orchestrator · Blackboard · MessageBus · ToolRegistry        │
│  · SolverEngine · SandboxManager · CheckpointGate · Budget    │
├─────────────────────────────────────────────────────────────┤
│  Agent Layer  角色化 LLM agents（SDK subagent 实例）           │
│  Professor · Postdoc · PhD · MLEngineer · SWEngineer · Reviewer│
└─────────────────────────────────────────────────────────────┘
              │                                  │
        Claude Agent SDK                   Docker Sandbox
        (会话/工具/subagent)               (代码执行/实验)
```

设计原则：**Workflow 决定"做什么和顺序"，Harness 决定"怎么协作与执行"，Agent 只负责"扮演角色产出内容"**。三层解耦，便于替换底层 SDK 或执行后端。

---

## 二、Agent 角色层（对标论文角色）

每个角色 = 一个带专属 system prompt + 工具子集的 SDK subagent。角色无状态，所有共享信息走 Blackboard。

| 角色 | 职责 | 主要工具 | 出现阶段 |
|------|------|----------|----------|
| **Professor**（导师/评审主导） | 设定研究方向、把关质量、生成评审意见与打分 | 读 Blackboard、Reviewer 评分模板 | 检查点、评审 |
| **Postdoc** | 与 PhD 协作产出实验计划、把关方法论 | 文献检索、Blackboard | 实验设计 |
| **PhD Student** | 文献综述主力、计划细化、解释结果 | arXiv/检索、读写 Blackboard | 全程 |
| **ML Engineer** | 写并迭代实验代码（mle-solver 驱动） | 代码编辑、沙箱执行、读数据 | 实验执行 |
| **SW Engineer** | 数据准备、环境/依赖、工程脚手架 | 文件操作、沙箱、依赖安装 | 数据准备 |
| **Reviewer**（可多实例） | 模拟 NeurIPS 风格评审，多维打分 | 评分 rubric、读论文草稿 | 论文精炼 |

角色协作以"对话回合"形式发生（如 PhD ↔ Postdoc 反复磋商实验计划直到达成一致），由 Harness 的 dialogue controller 管理回合数上限与收敛判定。

## 三、Multiagent Harness 层（设计重点）

Harness 是一个常驻运行时，由以下模块组成。每个模块给出**职责、接口契约、关键设计决策**。

### 3.1 Orchestrator（编排器）
- **职责**：驱动 Workflow 状态机，决定下一步激活哪个 agent / solver，注入上下文，收集产出，处理转移。
- **执行模型**：以"任务（Task）"为单位调度。Task = {目标, 指派角色, 输入上下文引用, 产出 schema, 重试策略}。
- **并行 vs 串行**：阶段间串行（有依赖）；阶段内可并行（如多 Reviewer 同时评分、多文献并行检索 → fan-out/fan-in，借助 SDK 的并行 subagent 能力）。
- **关键决策**：Orchestrator 本身**不写业务逻辑**，只读 Workflow 定义的状态图执行，保证流程可配置、可重排。

### 3.2 Blackboard（共享状态 / 黑板）
- **职责**：所有 agent 的唯一共享记忆，替代 agent 间直接传大段文本。存储研究全过程的结构化制品（artifacts）。
- **数据模型（命名空间分区）**：
  - `idea` / `lit_review`（文献条目+摘要）/ `plan`（实验计划）/ `dataset`（数据描述）/ `code`（当前最优程序）/ `runs`（实验记录+指标）/ `figures` / `paper`（分节草稿）/ `reviews`（评分） / `decisions`（检查点决议）。
- **访问契约**：agent 通过引用（key/版本号）读写，避免把全量内容塞进每次 prompt —— **只注入与当前 Task 相关的切片**（上下文裁剪是 token 成本与质量的核心）。
- **版本化**：制品可版本化（如 `code@v3`、`paper.method@v2`），支持 solver 的"保留最优 + 回滚"。
- **持久化**：落盘为单一 run 目录（JSON + 文件），支撑断点恢复（复用当前项目 `done.txt` 风格的 resume-safe 思路）。

### 3.3 MessageBus（通信协议）
- **职责**：规范 agent↔harness、agent↔agent（经 harness 中转）的消息格式。
- **消息 schema（结构化）**：`{from_role, to, intent, blackboard_refs[], payload, requires_ack}`。intent 枚举如 `propose / critique / approve / request_revision / handoff / report`。
- **关键决策**：**禁止 agent 间私聊明文长文本**，一律走结构化 intent + Blackboard 引用。这让对话可审计、可截断、可重放。
- **对话控制器**：管理多回合磋商（PhD↔Postdoc、作者↔Reviewer）的回合上限、收敛判据（达成 approve 或达到 max_turns）。

### 3.4 ToolRegistry（工具注册与路由）
- **职责**：统一注册工具，按角色授权暴露工具子集（最小权限）。
- **工具分类**：
  - 检索类：arXiv/语义检索、网页抓取（文献综述）。
  - 代码类：文件读写/编辑、依赖管理。
  - 执行类：沙箱运行（唯一入口到 SandboxManager）。
  - 写作类：LaTeX 编译、图表生成、引用管理。
- **路由**：所有"执行代码"工具调用强制经 SandboxManager，agent 无法直接触达宿主机。
- **关键决策**：工具授权按角色绑定（如只有 ML/SW Engineer 能调沙箱执行），降低误操作与越权。

### 3.5 SolverEngine（迭代精炼引擎 —— 系统的"实验/写作发动机"）
对标论文的 **mle-solver** 与 **paper-solver**，抽象成统一的"提案-评估-择优"迭代循环，两个子类共享框架：

- **通用循环**：
  1. 维护一个 candidate 池（保留当前 top-K 最优制品）。
  2. 每轮：基于最优制品生成"修改命令"（如 EDIT/REPLACE 某段代码或某节论文）。
  3. 应用修改 → 评估 → 打分 → 若优于现有则纳入池，否则丢弃（带自我反思）。
  4. 直到达到分数阈值 / 迭代上限 / 收益停滞。

- **MLE-Solver（实验执行）**：
  - 评估 = 在 **Docker 沙箱**内实跑代码 → 捕获 stdout/stderr/指标/异常。
  - 打分 = 可运行性 + 指标达成 + 与计划一致性；编译/运行错误触发自动修复回合。
  - 产出写入 `code` / `runs` / `figures`。

- **Paper-Solver（论文撰写）**：
  - 按节生成（Abstract/Intro/Related/Method/Experiments/Results/Conclusion），逐节精炼。
  - 评估 = LaTeX 可编译 + 内部一致性 + Reviewer 打分（NeurIPS rubric：质量/清晰度/原创性/意义）。
  - 集成 `lit_review` 自动插入引用。

- **关键决策**：把"实验"和"写作"统一为同一个带评分的迭代搜索，是系统质量的核心；评分函数是可插拔模块（不同领域可换 reward）。

### 3.6 SandboxManager（Docker 沙箱）
- **职责**：为每次实验/代码评估提供隔离、可复现、资源受限的执行环境。
- **生命周期**：按 run 起容器（基础镜像预装常用 ML 依赖）→ 挂载只读数据卷 + 可写工作区 → 执行 → 回收 → 清理中间产物（沿用当前项目"跑完即清理省盘"的做法）。
- **资源治理**：CPU/内存/超时/无网络（或白名单）限制；超时与 OOM 作为可恢复错误反馈给 MLE-Solver。
- **可复现**：镜像 tag + 依赖锁文件 + 随机种子记录入 `runs`，保证实验可重跑。
- **安全**：容器内执行 LLM 生成代码，默认断网、非 root、文件系统隔离；这是"全自动跑未知代码"的安全底座。

### 3.7 CheckpointGate（人机检查点）
- **职责**：实现"全自动 + 关键检查点"。在预设节点暂停，向人呈现当前 Blackboard 摘要，等待 approve / edit / reject。
- **默认检查点**：①选题与文献综述确认 ②实验计划确认 ③实验结果确认 ④投稿前论文确认。
- **机制**：检查点 = Workflow 状态机里的阻塞节点；决议写入 `decisions`；支持人直接编辑 Blackboard 制品后继续（人的修改作为高优先级上下文注入后续 agent）。
- **可降级**：检查点可配置开关，便于在"完全自动"基准测试与"co-pilot"日常使用间切换。

### 3.8 BudgetController（预算与防失控）
- **职责**：全局 token / 时间 / 迭代次数预算，防止 solver 死循环或失控烧钱。
- **机制**：每个 Task / solver 循环带配额；接近上限时强制收敛或上报检查点；记录每阶段成本供事后分析。

### 3.9 错误处理与恢复
- 分级：可恢复（代码报错→自动修复回合）、需介入（连续失败超阈值→升级到检查点）、致命（环境/配额→停机并落盘可恢复）。
- 借鉴当前项目的 resume-safe：全程制品落盘，崩溃后从最近 Blackboard 版本恢复，不重跑已完成阶段。

## 四、Workflow 阶段（状态机）

对标论文三阶段，细化为带检查点的状态图：

1. **文献综述（Literature Review）**
   - PhD 用检索工具收集→筛选→摘要相关文献 → 写入 `lit_review`。
   - 【检查点①】人确认选题与文献范围。

2. **实验（Experimentation）**
   - **计划制定**：PhD ↔ Postdoc 多回合磋商 → `plan`。【检查点②】
   - **数据准备**：SW Engineer 准备数据/环境 → `dataset`。
   - **运行实验**：MLE-Solver 在 Docker 内迭代代码 → `code`/`runs`/`figures`。
   - **结果解释**：PhD 解读指标 → 写入 `runs.analysis`。【检查点③】

3. **论文撰写（Report Writing）**
   - Paper-Solver 逐节生成 LaTeX → `paper`。
   - 多 Reviewer 并行打分 → `reviews` → 据此精炼（回到 Paper-Solver）。
   - 【检查点④】投稿前人确认 → 产出最终 PDF/LaTeX。

## 五、制品与目录布局（建议）

```
runs/<run_id>/
  blackboard.json        # 版本化共享状态
  decisions.json         # 检查点决议
  lit_review/            # 文献条目
  code/                  # 各版本实验代码（code@vN）
  experiments/           # 每次跑的日志/指标/figures
  paper/                 # 分节草稿 + 最终 LaTeX/PDF
  logs/                  # harness 与 agent 调用追踪
  budget.json            # 成本记录
```

## 七、验证方式（实现后如何端到端验证）

- **单模块**：Blackboard 读写/版本/恢复；SandboxManager 起停/超时/断网；MessageBus schema 校验。
- **Solver 闭环**：给一个玩具 ML 任务（如小数据集分类），验证 MLE-Solver 能迭代出可运行、指标改善的代码；Paper-Solver 能产出可编译 LaTeX。
- **端到端冒烟**：给一个简单 research idea，全自动跑通三阶段 + 四检查点，产出论文草稿；检查每个检查点能正确暂停/恢复。
- **失控防护**：注入死循环/报错代码，验证 Budget 与错误升级机制生效。
- **复现性**：同一 run 重跑，验证种子/镜像锁带来的结果一致性。
