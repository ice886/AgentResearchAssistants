# 架构设计（Architecture Design）

> 配套文档：`设计方案.md`（需求与高层设计）。本文是其技术架构细化，给出组件接口契约、数据模型、控制流、SDK 映射与并发模型，作为实现蓝图。

## 0. 设计约束回顾

| 维度 | 选定取向 | 对架构的影响 |
|------|----------|--------------|
| Harness 底层 | Claude Agent SDK | 角色=subagent，工具=SDK tool，会话=SDK session；自研编排/状态/求解层 |
| 自治程度 | 全自动 + 关键检查点 | 状态机需支持阻塞节点 + 暂停/恢复 + 人工编辑注入 |
| 执行环境 | Docker 沙箱 | 代码执行强隔离；唯一执行入口 SandboxManager |

技术栈：Python 3.11+ · Claude Agent SDK · Docker SDK for Python · Pydantic（schema 校验）· asyncio（并发）· 文件系统持久化（JSON + 制品文件）。

## 1. 分层架构与依赖方向

```
            ┌──────────── CLI / API 入口 (run idea) ────────────┐
            ▼                                                    │
┌─────────────────────────────────────────────────────────────┐│
│ Workflow Layer   ResearchPipeline (状态机定义, 数据驱动)        ││
│   - StateGraph: nodes(阶段) + edges(转移条件) + checkpoints    ││
└───────────────┬─────────────────────────────────────────────┘│
                │ 调用                                            │
┌───────────────▼─────────────────────────────────────────────┐│
│ Harness Layer  (运行时, 无业务逻辑)                            ││
│   Orchestrator ──drives──> 各模块                              ││
│   Blackboard · MessageBus · ToolRegistry · SolverEngine       ││
│   SandboxManager · CheckpointGate · BudgetController          ││
└───────────────┬─────────────────────────────────────────────┘│
                │ 实例化/调用                                     │
┌───────────────▼─────────────────────────────────────────────┐│
│ Agent Layer   RoleAgent (SDK subagent 封装)                   ││
│   Professor/Postdoc/PhD/MLEngineer/SWEngineer/Reviewer        ││
└───────────────┬─────────────────────────────────────────────┘│
                │ 依赖                                            ▼
┌───────────────▼─────────────┐   ┌──────────────────────────────┐
│ Claude Agent SDK            │   │ Docker Engine                │
└─────────────────────────────┘   └──────────────────────────────┘
```

**依赖规则（单向，自上而下）**：Workflow 只依赖 Harness 接口；Harness 只依赖 Agent 与基础设施抽象；Agent 只依赖 SDK。下层不得反向 import 上层。Orchestrator 持有所有 Harness 模块的引用，是唯一的协调点。

## 2. 核心数据模型（Blackboard Schema）

Blackboard 是系统的"单一事实来源"。所有制品用 Pydantic 模型定义，强 schema、可版本化、可序列化。

### 2.1 制品基类
```
Artifact (抽象)
  ├─ id: str                  # 命名空间.键, 如 "code.main"
  ├─ version: int             # 单调递增
  ├─ created_by: RoleName     # 产出角色
  ├─ created_at: ts
  ├─ parent_version: int|None # 支持回滚链
  ├─ score: float|None        # solver 评分(若适用)
  └─ payload: <子类定义>
```

### 2.2 命名空间与 payload
| 命名空间 | 制品 | payload 关键字段 |
|----------|------|------------------|
| `idea` | ResearchIdea | title, motivation, constraints, dataset_hint |
| `lit_review` | LitEntry[] | arxiv_id, title, summary, relevance, citation_key |
| `plan` | ExperimentPlan | hypotheses[], methodology, metrics[], success_criteria |
| `dataset` | DatasetSpec | source, schema, split, prep_script_ref |
| `code` | CodeArtifact | files{path→content}, entrypoint, deps[] |
| `runs` | RunRecord[] | code_version, metrics{}, stdout_ref, status, seed, analysis |
| `figures` | Figure[] | path, caption, source_run |
| `paper` | PaperDraft | sections{name→latex}, bib_refs[], compile_status |
| `reviews` | ReviewScore[] | reviewer_id, dims{quality,clarity,originality,significance}, comments |
| `decisions` | Decision[] | checkpoint_id, verdict(approve/edit/reject), human_note, ts |

### 2.3 版本化与并发控制
- 写入用**乐观锁**：`write(artifact, expected_version)`；版本不匹配则拒绝，调用方重读再写（防止并行 agent 覆盖）。
- 每次 `set` 产生新 version，旧版本保留（支持 solver 回滚 `code@v3 → code@v2`）。
- 大文件（数据、figure、stdout）存盘，Blackboard 只存引用（`*_ref` 字段 = 相对路径）。

## 3. Harness 组件接口契约

每个模块定义为一个 Python class，下列为关键方法签名（接口级，非实现）。

### 3.1 Blackboard
```
get(id, version="latest") -> Artifact
set(artifact, expected_version) -> int      # 返回新版本号, CAS
history(id) -> list[version]
slice(refs: list[str], budget_tokens) -> ContextBundle  # 上下文裁剪
snapshot() / restore(run_id)                # 持久化 ↔ 恢复
subscribe(namespace, callback)              # 供 MessageBus/日志
```
关键决策：`slice()` 是控 token 的核心 —— 按相关性 + 预算裁剪/摘要后再注入 prompt，绝不全量灌入。

### 3.2 Orchestrator
```
run(pipeline: StateGraph, idea) -> RunResult
  loop:
    node = graph.current()
    if node.is_checkpoint: CheckpointGate.gate(node) → 阻塞
    else: dispatch(node)  # 生成 Task → 指派 agent/solver
    next = graph.transition(node, result)
dispatch(task: Task) -> TaskResult
```
Task 模型：`{goal, role, input_refs[], output_schema, retry_policy, budget}`。

### 3.3 MessageBus
```
send(Message) -> MessageId            # 经 harness 中转, 落审计日志
dialogue(participants, topic, max_turns, converge_fn) -> Transcript
```
Message schema：`{from_role, to, intent, blackboard_refs[], payload, requires_ack}`，intent ∈ {propose, critique, approve, request_revision, handoff, report}。`dialogue()` 封装多回合磋商（PhD↔Postdoc、作者↔Reviewer），由 `converge_fn` 判定收敛或触顶 `max_turns`。

### 3.4 ToolRegistry
```
register(tool, allowed_roles: set[RoleName])
tools_for(role) -> list[Tool]         # 最小权限子集
```
执行类工具（run_code）内部只能调 SandboxManager，agent 无直达宿主机路径。

### 3.5 SolverEngine（基类 + 两子类）
```
class Solver(ABC):
  solve(target_ref, max_iters, score_threshold) -> Artifact
  _propose(best) -> EditCommand        # 生成修改命令
  _apply(edit, base) -> candidate
  _evaluate(candidate) -> Score        # 抽象, 子类实现
  _select(pool, candidate) -> pool'    # top-K 择优 + 反思

MLESolver._evaluate = SandboxManager.run() → 指标/异常
PaperSolver._evaluate = latex_compile + Reviewer.score
```
统一的"提案-应用-评估-择优"循环；`_evaluate` 即可插拔 reward。

### 3.6 SandboxManager
```
spawn(image_tag, mounts, limits) -> Container
run(container, cmd, timeout) -> ExecResult{stdout, stderr, exit, metrics}
teardown(container)                   # 回收 + 清理中间产物
```
默认：非 root、`--network none`（或白名单）、CPU/mem/timeout 限额；OOM/超时归为可恢复错误返给 MLESolver。

### 3.7 CheckpointGate
```
gate(checkpoint) -> Decision          # 渲染 Blackboard 摘要 → 等待人
  verdict: approve | edit | reject
  edit → 人改 Blackboard 制品, 作为高优先级上下文注入后续
enabled: bool                         # 可全局关闭(纯自动基准模式)
```

### 3.8 BudgetController
```
charge(tokens, role, phase); check(scope) -> bool
on_near_limit -> 强制收敛 | 升级检查点
report() -> CostBreakdown
```

## 4. 关键控制流（时序）

### 4.1 实验阶段（MLE-Solver 闭环）
```
Orchestrator
  → dispatch(Task: 运行实验, role=MLEngineer)
  → MLESolver.solve(code.main):
       loop until score≥θ or iters用尽 or budget耗尽:
         _propose: MLEngineer(SDK) 读 plan+code切片 → EditCommand
         _apply → candidate code@vN+1
         _evaluate: SandboxManager.spawn → run → ExecResult
            ├─ 报错/超时 → 反馈错误, 下一轮自动修复
            └─ 成功 → metrics
         _select: 比 score, 优则纳入池(写 Blackboard), 劣则丢
       → 写 runs + figures
  → BudgetController.charge 全程计费
  → PhD 解读 metrics → runs.analysis
  → CheckpointGate.gate(检查点③)
```

### 4.2 计划磋商（dialogue 收敛）
```
MessageBus.dialogue([PhD, Postdoc], topic=plan, max_turns=N):
  PhD.propose(plan@v1) → Postdoc.critique → PhD.revise(plan@v2) ...
  converge_fn: Postdoc 发出 intent=approve → 收敛
  → plan 定稿 → CheckpointGate.gate(检查点②)
```

### 4.3 暂停 / 恢复
```
任意时刻 → Blackboard.snapshot()（每节点结束自动落盘）
崩溃/中断 → Orchestrator.run(resume=run_id):
  restore Blackboard → 跳过 decisions 中已 approve 的节点
  从最近未完成节点继续（resume-safe, 不重跑已完成阶段）
```

## 5. Claude Agent SDK 映射

| 架构概念 | SDK 机制 |
|----------|----------|
| RoleAgent | 一个 subagent（专属 system prompt + 工具子集 + model 配置） |
| 角色工具授权 | subagent 的 tools 白名单（ToolRegistry.tools_for 注入） |
| 阶段内并行（多 Reviewer / 多文献检索） | 并行 subagent 调用（fan-out / fan-in） |
| 结构化产出 | SDK structured output / 强制 tool 调用 → 校验为 Pydantic 制品 |
| 工具（检索/编辑/执行/写作） | SDK 自定义 tool；run_code tool 路由到 SandboxManager |
| 多回合磋商 | harness 层 dialogue 循环驱动两个 subagent 交替 |
| 预算/追踪 | 包裹 SDK 调用记录 token → BudgetController + logs |

注：编排、状态、求解循环、检查点**不依赖 SDK**，由 harness 自研，便于将来替换底层。

---

## 6. 并发模型

- **运行时**：asyncio 单事件循环。Orchestrator 串行驱动阶段；阶段内 fan-out 用 `asyncio.gather`。
- **并行边界**：仅无依赖任务并行（多 Reviewer 打分、多文献检索、solver 内多 candidate 评估）。Blackboard 写入用 CAS 乐观锁解决竞争。
- **沙箱并发**：SandboxManager 维护容器池，限制最大并发容器数（资源治理）；每 candidate 评估一容器，evaluate 完即回收。
- **背压**：BudgetController 是全局闸门，逼近上限时收窄并发并触发收敛。

---

## 7. 错误处理与恢复（分级）

| 级别 | 触发 | 处理 |
|------|------|------|
| 可恢复 | 代码报错/编译失败/超时/OOM | 作为反馈进入 solver 下一轮自动修复 |
| 需介入 | 同一 Task 连续失败 > 阈值 / solver 收益停滞 | 升级到 CheckpointGate 请人判断 |
| 致命 | 沙箱不可用 / 预算耗尽 / SDK 持续错误 | 停机，snapshot 落盘，标记可 resume |

所有节点结束即 snapshot；恢复时按 `decisions` 跳过已确认阶段（沿用 PDF 项目 resume-safe 思路）。

    orchestrator.py

    base.py                       # RoleAgent(SDK subagent 封装)

复用现有项目模式：`config.py` 集中配置、resume-safe（`done`/`decisions`）、跑完即清理沙箱中间产物。

## 9. 实现里程碑（建议顺序）

1. **骨架 + 数据层**：models.py + blackboard.py（CAS/版本/持久化）+ config。可单测。
2. **沙箱**：SandboxManager（起停/限额/断网/超时）。独立可测。
3. **Agent 封装 + ToolRegistry**：RoleAgent over SDK + 工具授权。
4. **SolverEngine**：base + MLESolver（接沙箱）→ 玩具 ML 任务跑通迭代。
5. **MessageBus + dialogue**：计划磋商收敛。
6. **Orchestrator + Workflow + CheckpointGate**：串起三阶段 + 检查点。
7. **PaperSolver + Reviewer**：LaTeX 闭环。
8. **预算/恢复/e2e 冒烟**：端到端跑通一个简单 idea。

每个里程碑对应 §7 验证方式中的一类测试。

## 10. 待定项（影响实现细节，非阻塞）
